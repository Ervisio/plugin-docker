# Git logins moved to an admin folder so token and deploy key reach git (v1)

A correct token or deploy key failed with "could not read Username". The git-* commands are `admin` + `adminUnlessGroup: docker`, so for a user outside the docker group they run as root. The plugin, however, wrote the `.cred`/`.key` files through `sdk.files` into `~/.config/...`, and that path always resolves to the user's own home, not root's. The fix moves the login files to `/opt/stacks/.ervisio-git`, which follows the same identity rule as the commands. The folder is created by a new `git-auth-init` command and each file is chmodded to 600 by a new `git-auth-lock` command, because OpenSSH refuses a 0644 key. The old `~` location stays as a read-only fallback, and `explainGitError` now separates "no login was sent" from "login refused". The manifest was hand-mirrored and nothing was executed: the sandbox shell fails on every command, so `gen-manifest --check`, typecheck and tests have not been run.

Watch for: the new error messages tell users to "enter the login again" for an existing stack, but no screen lets them do that (confirmed). Legacy deploy-key stacks whose key is refused get reported as "saved login missing" (confirmed). Files at mode 600 are bound to whoever wrote them, so a second docker-group user cannot use another user's login (likely).

**Verdict**: APPROVED

## High-level view

The root-cause analysis matches the manifest: `capabilities.files` declares `/opt/stacks` read/write with `admin: true, adminUnlessGroup: docker`, the same rule as the git-* commands. So the account that writes the login file is the account git runs as. The `~` write folder has no admin flag, which is exactly the mismatch that produced the reported error. Login file I/O now goes through a local `getSdk().files` wrapper with no paired-server `env`, which matches where the git commands run.

Every git-* argv now chains the helpers in this order: reset, the `store` helper on the admin folder, then the legacy `~` helper. The legacy helper is a shell function that only answers `get`, so git's `store`/`erase` calls never copy a token into root's home. ssh gets both `-i` paths. The new commands are tightly bounded: `git-auth-lock` only accepts `<stack>.cred|.key` with no `/` or leading dot, and `{0}` is spliced into the shell helper only after the stack-name pattern has been checked. The hand-mirrored manifest matches what the generator would emit: same key order, same escaping of `\.` and `\"$1\"`, and the new entries sit right after `git-status`.

The error mapping is where the gaps are. `credMissing` only looks in the new folder, so legacy ssh stacks are misreported. Both the new messages and the CHANGELOG point users to re-entering a login, which the UI only allows by recreating the stack.

### Identity rule behind /opt/stacks/.ervisio-git

`git-auth-init` creates the folder as root:docker 2770 (user:docker 2770 when a docker-group user runs it first). Each file sits at 0644 only briefly, inside a folder that just root and the docker group can traverse, before it is locked.

The cost of mode 600 (likely): the file belongs to whoever saved it. `GitMeta.by` documents that updates run as the stack's owner, so scheduled jobs are fine. But an interactive Check or Update by a second docker-group user cannot read the token. git then reports "could not read Username", and since the file exists in the folder, the user sees `noLogin` with advice they cannot act on. This was equally broken before (home-folder files), so it is not a regression. However, the new folder is group-shared, so the plugin could make tokens group-readable without changing the trust boundary: docker group membership is already root-equivalent.

### Legacy fallback and helper semantics

```
credential.helper=
credential.helper=store --file /opt/stacks/.ervisio-git/{0}.cred
credential.helper=!f() { [ "$1" != get ] || git credential-store --file ~/.config/.../{0}.cred get; }; f
core.sshCommand=ssh -i /opt/stacks/.ervisio-git/{0}.key -i ~/.config/.../{0}.key ...
```

The read-only legacy helper is a good catch: a plain `store` helper would get `store` after every successful login and leave a copy of the token in root's home that `removeCredentials` never deletes. The fallback only helps accounts whose identity already matched before the fix (docker-group users). The administrator case from the bug report has no readable legacy file and must re-enter the login. For a new clone, which is the user's situation, that is fine.

### Error classification and the credMissing remap

`git()` turns turns `noLogin` or `ssh` into `credMissing` when `loginFileMissing(name, auth)` finds no file in `GIT_AUTH_DIR`. For tokens this is sound, because `noLogin` means neither helper returned anything. For ssh it is not (confirmed). A legacy deploy-key stack used by a docker-group user offers the `~` key. If GitHub then refuses it ("Permission denied (publickey)") or host-key verification fails, the new-folder file is missing and the user is told the saved login cannot be found, which hides the real cause. `loginFileMissing` also returns true when the list call itself fails (for example `needs_admin`), which produces the same message for an unrelated reason.

### Re-entering a login

Every new message ends with "enter the login again" / "Save the key again", and the CHANGELOG says "enter the login again if one still fails". The only callers of `storeCredentials` are `GitStackPage.check()` and `cloneStack`, both on the new-stack page. `StackPage` only calls `removeCredentials` (confirmed). A user with an existing stack therefore has to detach or delete it and add it again, and nothing tells them so.

### Tests

`test/gitcreds.test.ts` (SDK mock) and `test/automation.test.ts` cover the write-then-lock flow, no `{env}` on login files, the helper order and the `git-auth-lock` pattern, and `credMissing` vs `noLogin` for tokens. Not tested: the `credMissing` remap for ssh, especially a legacy key that is present but refused; `loginFileMissing` when the list call errors. None of the tests have been run.
