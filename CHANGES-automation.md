# Changes from the automation branch (feat/automation)

Needs Ervisio 0.5 or later: the manifest now declares `jobs` and `notify`, which older consoles reject. The plugin builds against SDK `release/0.2`.

- Git stacks: "New stack" now offers "From a Git repository". Give the address (https, http, ssh), a branch or tag (Check lists what the repository has), the compose file inside it and a sign-in: none, an access token, or a deploy key. The repository is cloned into `/opt/stacks/<name>` and, if you want, deployed. Needs `git` on the machine; the page says so when it is missing.
- Git stacks: the stack page shows the repository, branch or tag, compose file, sign-in and the commit it is at (hash, subject, author, date). "Check for updates" tells whether the branch moved, "Pull and redeploy" fetches, replaces the files, pulls the images and redeploys.
- Git stacks: tokens and deploy keys are saved in your private plugin folder (`~/.config/ervisio/plugins/docker/git`, only you can read it) and never appear in addresses, command lines, job settings or the activity log. Updates run as the user who added the stack.
- Git stacks: editing a Git stack's compose file warns that the next update replaces the change, and lists files that differ from the repository. "Detach from Git" keeps the files, removes the Git link, the saved sign-in, the automatic update and the webhook.
- Automatic updates: a switch on every Git stack. Pick an interval (5 minutes to a day) or a time of day, and when to be told (never, on success, on failure, both). A background job fetches, compares, pulls, redeploys and notifies, also when nobody has Ervisio open. "Run now" and the last result are on the stack page.
- Redeploy webhooks: on every managed stack and every container. A web address that, when called (a registry, a CI job, a push hook), redeploys a plain stack (pull images, up), a Git stack (pull the repository, up) or a container (pull the image again, recreate with the same settings, through Watchtower). The address is shown once; make a new one or revoke it any time. The last calls are listed with each step's output.
- Notifications: alert rules can also send through the notification channels set up in Settings › Notification channels (email, Telegram, ntfy, Gotify, webhook). A switch per rule, and "Test notification channels" on the Alerts page. A page and a widget open together do not send the same alert twice.
- Scheduled volume backups: Volumes › "Schedule backups" (or the clock on a volume). Every hour to week, or at a time of day, keep the newest N, notify as you choose. Each backup is a tar file in `/var/backups/ervisio-docker/<volume>/<date>.tar`; the page lists the files, runs a backup now and removes schedules. A schedule for a volume that does not exist fails instead of creating an empty one.
- Import from Portainer (Tools): finds the Portainer container (also a stopped one), reads its database through the Docker API and lists stacks, registries, custom templates and environments. Import what you select: stacks to `/opt/stacks` with relative bind mounts made absolute (as "Move" does), Git stacks as Git stacks (with their branch, compose file, variables and automatic update interval), registries as saved logins, custom templates as custom templates. Portainer logins for Git repositories and registries are copied only after you say so. Environments cannot be created by a plugin: the page lists what each could become in Settings › Environments, with its address, and copies a checklist. Reads Portainer 2.19 and 2.45 databases. An encrypted database (Portainer started with a secret) is explained and nothing is imported.
- Fix: the "Move" and delete code now handle stacks whose compose file is in a sub-folder, and delete a Git checkout completely.
